# WBS06 stock v551 investigation

Analysis and hardware tests, 12–15 November 2026. Stock v551 boots on the tested
WBS06, but its BLE connection repeatedly disconnects after about 40 seconds on
the tested Mac. **A direct Classic Bluetooth OTA from stock v551 to YOW v127
has now passed**, including automatic reboot and independent version/slot
checks. Suppressing just v551's early BLE parameter request also enabled a
complete **diagnostic-v551 → YOW v127 BLE OTA**, retaining v551's original
controller firmware. This is a firmware-side fix, not yet a bridge-only
workaround for untouched stock v551. The successful Classic route used a private
test harness. Bridge 0.4.10 integrates that exchange, blocks stock-v551 BLE OTA
and directs users to **Scan Classic**, then back to BLE after updating. The
integrated flow has regression coverage; the hardware result below remains the
private-harness qualification on macOS, with Linux WBS06 Classic untested. YOW
generation continues to use stock v1181 and produces v127.

## Image and hardware lineage

[Stock download](http://cdnfw.withings.net/wbs06/wbs06_551_z7Q6Dr.bin):

- Version: **551**, build `2019-01-18 14:32:41+01:00`.
- Length: **838,532 bytes**.
- SHA-256: `670c1baf639130873ca74e5ce352541d8f7804e8faaedb7ab4e5f1dbb86b7c27`.
- SHA-1: `287f68d1be30a137dbe4ed75d97f6ecfe055bf68`.
- Container, section and whole-file CRCs pass; version words agree.

The application uses the same flash mapping and initial stack pointer as
v1181. Its bootloader v4 and Wi-Fi image are byte-identical to v1181's. The
Bluetooth payload differs, but is byte-identical to the older WBS06 v371
payload and targets the same BCM4343A1 controller family. Both images contain
the same Wi-Fi board identifiers.

Stock v551 also booted on the same physical scale that runs stock v1181 and
YOW v127, and returned a valid BLE identity. There is no positive evidence here
for a separate hardware variant. These
matches do not exclude board revisions: the reported hardware field
`0xffffff` is not a useful discriminator on its own.

Withings' [official release notes](https://support.withings.com/hc/en-us/articles/115009286888-Body-What-s-new-with-the-Body)
describe v551 as adding features for Comme J'aime users. Partner/account or
rollout targeting is therefore plausible, but the binary cannot establish
why the server offers v551 to a particular device. The firmware reads its
manufacturer ID from configuration, and the current offer probe does not
reproduce every field of v551's original session request.

## Bluetooth OTA

The missing `CHUNKED_UPDATE` implementation concerns the newer HTTP update
path. **Bluetooth OTA is present in v551.** Application addresses below use
the image's `0x4000` load address:

| Behaviour | Evidence |
| --- | --- |
| MTU query `0x155` unsupported | Dispatcher `0x36454` returns unknown command `-3`. |
| OTA START `0x401` supported | Handler `0x360e8`, callback `0x21d24`, flash initialization `0x32ce8`. |
| BLE data limit | Callback `0x22560` sets `min(ATT_MTU, 135) - 9`; START advertises that value. |
| Data buffering | `0x21de0` → `0x4fbb4` → `0x32c58`, with 256-byte flash pages and readback checks. |
| Acknowledgments | Empty `0x402` every 15 BLE packets; empty `0x403` on completion. |
| Classic data limit | Context initializer `0x36a0a–0x36a22` sets 512 bytes; hardware START confirmed 512 bytes and window 4. |
| Destination | `0x4fc3a`: lower version when both slots are valid and gold-marked. |
| Boot request | OTA initialization records the selected bank; completion requests the disconnect/reboot sequence. |

The stock BLE packet offer is **126 bytes**, even when the transport permits
132-byte ATT writes. At ATT MTU 23, the offer is 14 bytes. The bridge now skips
`0x155` for a matching v551 identity so it can show the warning, and refuses BLE
OTA before START. Classic probes require the matching Body/bootloader-4/hardware-
`0xffffff` identity and v551, then enforce the 512-byte/window-4 START response.
Configuration writes stay disabled until YOW is running and connected over BLE.

The exact stock v551 hash has a separate inspection profile for its older
Bluetooth section and runtime-version location. Modified images do not inherit
that exception, including through `FLASH UNKNOWN`. The v1181 generation recipe
and its checks remain unchanged.

## Offline verification and limits

Unicorn executed the actual v551 dispatcher, MTU callback, slot selector,
START handler and data/page-buffering code. Hardware I/O, RTOS events and
slot-validity reports were stubbed. Full stock v1181 and YOW v127 files staged
byte-for-byte into simulated flash, with the expected ACKs and the other
v1181 slot unchanged. YOW v127 also passed with 20-byte data packets despite
a 126-byte START offer.

Bridge regressions cover BLE refusal before START, Classic identity normalization,
512-byte/window-4 transfers, final full and partial windows, insufficient transport
limits, invalid offers, mismatched identities, and failures of the modern MTU command.
An optional exact-image
test verifies that CRC-correct modifications cannot use the stock exception:

```sh
PYTHONPATH=bridge/src \
YOW_TEST_WBS06_551=/path/to/wbs06_551_z7Q6Dr.bin \
.venv/bin/python -m unittest discover -s bridge/tests -p 'test_firmware.py' -v
```

These checks alone do not demonstrate physical Bluetooth reliability or
compatibility with configuration written by newer firmware. The hardware
results below qualify what has actually been exercised.

### Hardware observations

A WBS06 running YOW v127 accepted all 838,532 bytes of stock v551 and returned
the OTA completion response. Two subsequent identity probes still reported
v127, so the return updater correctly refused to run: completion is not proof
that the requested firmware booted.

After a battery removal/reinsertion, the scale showed the stock Hello screen
and reported **v1181**. This confirmed the retained stock image remained bootable.

The experiment harness initially disconnected immediately after completion.
The firmware sends the reply before a delay and the reboot event, so the harness
was corrected to wait for the device to disconnect. Whether that timing
caused the initial result is unconfirmed.

A second transfer, from stock v1181, completed and the scale disconnected
itself. Its next BLE identity response reported **v551**, bootloader 4, with
the expected model and MAC. This confirms that v551 booted and its protected
identity exchange worked on this hardware.

The return transfer to YOW v127 began in that automatically resumed setup
session. v551 advertised 126-byte packets and a window of 15, and sent normal
progress acknowledgments. The connection dropped before completion; the
last periodic progress report recorded 57,204 of 905,364 bytes (6.3%). This
is a lower bound on bytes sent, not the exact disconnect offset. The scale
displayed Setup failed. A fresh button-driven setup session then reported
**v1181**, without a battery removal, confirming stock recovery after the
interrupted transfer. The cause was not established in that run; the later idle
tests and UART comparison below isolate a Bluetooth link failure.

The subsequent read-only probe closed its connection without completing
setup; the user again saw Setup failed. That display is not by itself a
diagnosis of an OTA or image-validation error. External slot contents were
not independently read. At this stage the v551-to-YOW hardware path remained
unqualified; the later Classic test below succeeded.

Recovery from stock v1181 to YOW v127 subsequently completed: all 905,364
bytes were acknowledged, the scale disconnected itself, and a fresh BLE probe
confirmed **v127**. The configured server/protocol and stored Wi-Fi SSID matched
the pre-test values. The Wi-Fi password is not exposed by the readback, and
this check did not exercise a Wi-Fi sync.

The Mac's Bluetooth log places the interrupted v551 connection approximately
40 seconds after connection establishment. At disconnect it records a pending
`LE_READ_REMOTE_FEATURES_PAGE_0` HCI command (`0x2016`), with internal status
634 and disconnect reason 734. These are recorded host-stack values, not
directly decoded Bluetooth controller error codes. This is a lead for
investigating the old Bluetooth stack; it does not yet establish which side
initiated the failure. Subsequent tests checked this lead without starting OTA.

A further stock-v551 transfer completed and its identity was confirmed again.
This time the connection was left idle after the probe, with a 60-second
stability check required before any return OTA. It disconnected after **39.35
seconds**, without sending OTA START or any image bytes. The Mac logged the
same pending Remote Features command and internal 634/734 statuses. The
connection failure can therefore occur independently of the OTA data path.

A fresh button-started setup session reproduced it: v551 answered the identity
probe, then disconnected after **39.83 seconds** during the idle check, again
with no OTA START sent and the same host errors. This rules out the resumed
setup session as a necessary trigger. No return image was written during either
stability check. UART tracing followed on 15 November.

### UART comparison, 15 November

UART independently confirmed valid, gold-marked external images of v551 and
v1181, with internal flash matching v551. Explicit boot selection could copy
either existing image into internal flash without rewriting the external slots.

A cold-boot button hold entered the factory-reset menu and booted the retained
v1181 image. The v551 UI has different hold callbacks for cold boot and normal
button wake; the cold-boot path can select factory reset. There is no evidence
that the configured hostname caused this event. Subsequent tests started setup
with the UART command `device_setup listen`, avoiding button timing. A retained
firmware image does not preserve the shared configuration: a later Wi-Fi read
returned no configuration value.

Fresh pairing directly on v551 timed out in SMP, including after forgetting
the device on the Mac. Pairing on v1181 succeeded. A fresh-boot v1181 connection
then passed a **60-second idle check and a second identity probe**. Booting v551
with that bond allowed its protected identity exchange, but the connection
dropped after **39.315 seconds**, again before any OTA command.

At that drop, the scale's UART reported HCI disconnect reason **`0x08`**:
[Connection Timeout](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/architecture,-mixing,-and-conventions/controller-error-codes.html),
the Bluetooth link supervision timeout. The Mac again reported a pending
Remote Features command and internal 634/734 statuses. This establishes a
Bluetooth link failure independently of Wi-Fi/hostname handling and OTA data
transfer. It does not identify the underlying controller/stack defect or prove
whether the older Bluetooth payload alone is responsible.

One attempt to invoke the UART setup command twice in the same v1181 boot
faulted in `ble_gatt_restore_cccds`. Later comparisons used one setup session
per fresh boot. This diagnostic-shell limitation should not be conflated with
the reproducible v551 link timeout.

Recovery through v1181 passed again: a second 60-second preflight succeeded,
all 905,364 YOW v127 bytes were acknowledged, and the scale rebooted itself.
Both the protected BLE identity and the two internal application version words
confirmed **v127**. UART verified valid, gold-marked external **v127 and v1181**
images. The configured HTTPS target remained intact; the Wi-Fi read still
returned no configuration value, requiring Wi-Fi setup again. This recovery
did not itself qualify a direct v551-to-YOW Bluetooth update.

### Cold-boot control and Classic OTA, 15 November

A genuine battery removal/reinsertion booted stock v551, independently confirmed
by UART and the internal application version word. Its protected BLE identity
passed, then the connection failed after **39.286 seconds** during the read-only
dwell. A warm-reset carryover from v1181 is therefore not required to reproduce
the BLE failure.

Static analysis identified an application-level negotiation change: v551 requests
10–22.5ms intervals and a one-second supervision timeout immediately after the
BLE connection event. v1181 requests 15–30ms and two seconds after pairing or
bond restoration. The Mac logs show the corresponding difference in timing and
parameters. This motivated the single-instruction experiment below; the static
comparison alone could not establish causality.

Stock v551 also exposes a working Classic Serial Port Profile. Discovery found
its radio address at product MAC + 1; the full WPP identity was checked against
the product MAC before any OTA. On this device, SDP returned channel 9 and the
RFCOMM MTU was 1,018 bytes. Classic passed a 60-second idle check followed by a
second identity request, without making a BLE connection.

The first Classic OTA attempt stopped because the private harness incorrectly
limited packets to the WS-30 size. START had already erased the destination
slot, but no firmware data was sent. The retained v1181 slot recovered the
scale on cold boot. Stock v551 was then fully reinstalled before retrying,
so the successful test used its own complete application and radio image.

The corrected Classic transfer used the firmware's **512-byte packet offer and
four-packet acknowledgment window**, matching the static handler. After another
60-second connection check, all **905,364 bytes** of pinned YOW v127 transferred
and the scale returned `0x403` completion. START through completion took about
36 seconds. The scale disconnected and rebooted automatically; UART reported
**old=551 new=127**. Both internal version words read 127, and UART verified
valid, gold-marked **v127 and v1181** external slots. A subsequent protected BLE
connection passed a 60-second idle check and a second v127 identity probe.

This proves a direct Classic OTA route on the tested Mac and WBS06. UART started
setup and recorded the boot/slot checks; the successful return image was sent
entirely through Bluetooth. Bridge 0.4.10 now handles the Classic discovery/identity
route, packet limits and initial connection timing, based on this exchange.
Fresh pairing on another Mac, Linux Classic, and a completely UART-free setup
sequence have not been qualified by this test. BLE OTA from untouched stock v551 remains
unreliable on this Mac.

### Deferred discovery and the early parameter request, 15 November

A staged BLE test separated connection establishment from application-requested
GATT discovery, notification subscription and the protected identity probe.
YOW v127 passed all stages, remaining connected for 140 seconds with two valid
identity replies. macOS still performs its own link and GATT operations; delaying
the application's discovery call does not suppress those OS operations.

Untouched stock v551 disconnected after **40.001 seconds**, before the application
requested discovery. A repeat after a fresh reset, with matching v551 CCCDs
restored instead of invalidated by a version change, failed after **39.999
seconds**. Both failures reproduced the pending Remote Features command on the
Mac. Deferring bridge discovery is therefore insufficient, and mismatched saved
CCCD versions are not required for the failure.

A private diagnostic image replaced only the `BL` at application address
`0x1c1d0` (container offset `0x18254`) with two Thumb NOPs. This skips the early
connection-parameter request; all other application bytes, version words,
Bluetooth/Wi-Fi resources and bootloader bytes were retained. Only the required
CRCs were additionally changed. The diagnostic deliberately still reports 551
but is **not stock firmware** and is not accepted by the production stock-image
exception.

The diagnostic was installed over Classic Bluetooth, then UART verified the
actual NOP bytes in internal flash and valid diagnostic-v551/v1181 external
slots. It passed the same staged BLE test: 60 seconds before discovery, discovery,
notification subscription, a protected identity probe, a further 60-second dwell
and a second identity probe. The harness disconnected intentionally after
**140.303 seconds**. The v551 controller firmware was unchanged throughout.

After a fresh reset, the diagnostic also passed the normal bridge's immediate
discovery/subscription/probe sequence and a 60-second preflight with a second
identity reply. A full **905,364-byte YOW v127 OTA over BLE** then completed,
using 126-byte packets and a 15-packet acknowledgment window. Transfer took
about eight minutes and sixteen seconds; the connection lasted over nine
minutes and the scale disconnected itself after completion.

UART recorded automatic reboot and **old=551 new=127**. Both internal application
version words read 127, and the external slots were independently verified as
valid, gold-marked **v127 and v1181**. The diagnostic image was therefore replaced
by the pinned YOW release; it was not left installed. A fresh BLE connection to
the restored v127 passed another 60-second dwell and two protected identity
probes.

This isolates the early application-level parameter request as a trigger for
the observed failure on this Mac/scale combination. It does not establish which
controller or host procedure mishandles that request, nor provide a bridge-only
workaround for an untouched stock-v551 device. Fresh pairing was not exercised
by this test; the existing bond was retained.

## Round-trip test

For a controlled experiment, if the two external slots contain valid,
gold-marked **v1181 and YOW v127**, the sequence is below. The successful v551
return used the private Classic harness; bridge 0.4.10 integrates its exchange.

1. Probe and record the currently running firmware. Send the pinned stock v551
   through Bluetooth OTA. It replaces the v127 slot and preserves v1181.
2. OTA requests booting the newly written v551 automatically. The shared v4
   bootloader's explicit-bank path at `0x828` does not require a version increase.
3. Re-enter setup mode, connect through Classic, confirm v551, wait at least
   60 seconds, and probe again.
   Only after that check passes, send pinned YOW v127. Since 551 is lower than
   1181, this replaces the same external slot. If the check fails, use UART to
   boot the retained v1181 image and recover through its working OTA path.
4. Reconnect through BLE and confirm v127. Read back settings, complete setup
   and verify Wi-Fi sync as a separate configuration check; the successful
   Classic round trip does not establish that shared configuration survived
   earlier factory-reset testing.

UART is not intrinsically required by the OTA protocol, but it provided recovery
and independent slot checks in this experiment. Bluetooth identity reports only
the running version, so slot preservation remains conditional without a slot
check. A preserved firmware slot is also not a backup of the shared
configuration database.
